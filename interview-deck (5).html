A redaction tool for audit & compliance, built with AI

  • Audit team's process: download report → run local script to highlight keywords → go through Adobe Pro one highlight at a time
  • Every user needed a paid Adobe Pro license
  • Once a word was redacted, it was gone — second reviewer couldn't verify it
  • Director spent ~1 year trying to get IBM to build a custom solution — rejected
  • We decided to build it ourselves — I led it

Design Choices

Why we built it this way

No database
  • File-based JSON sessions + file locking
  • Fast to build, easy to reason about at our scale
  • Tradeoff — doesn't scale across multiple instances without more work
Two separate queues
  • Session queue — serial, never cancelled (save/load/export)
  • Find queue — cancellable (search stops on file switch)
True redaction, not an overlay
  • PyMuPDF actual redaction, not visual overlay
  • Forensics-tested — visible + hidden text layer removed
Optimistic concurrency
  • Conflicting saves → 409, not a silent overwrite
  • Matters for second-reviewer collaboration

The Governance Layer

AGENTS.md — read by every AI session, first

Maps the project
  • Where the backend, frontend, and tests live — so AI isn't guessing every session
Documents pitfalls we'd already learned
  • File-based sessions aren't multi-process safe without a dedicated redesign
  • 401 and 403 are different outcomes — conflating them caused a real bug
Required workflow for any change
1
Confirm which layer is affected
2
Read the relevant files first
3
Make the smallest consistent change
4
Validate with the narrowest test first
5
Report what changed and what wasn't tested

Repo & Pull Request Management

Bitbucket, and where AI review actually happens

  • Code lives in Bitbucket
  • GitHub Copilot's automated PR review is GitHub-only — no native Bitbucket support
  • So review happens in the IDE: Copilot Chat checks the local diff against AGENTS.md before a PR
  • Flags logic issues, missed edge cases, anything touching session/auth
  • Final approval stays human — a teammate has to actually understand the change
Testing

Unit tests generated with the code. E2E — planned wide, shipped narrow.

Unit tests
  • AI generates the Vitest test file alongside the implementation
  • Same request — coverage built in, not bolted on after
E2E — honest scope
  • Planned: full scenario matrix, P0–P3, estimated coverage per area
  • Shipped: smoke suite — ~13 tests, P0 critical paths
  • Coverage % = planning estimate, not measured — said plainly
known gap — a few edge cases (Safari private mode, in-memory rate limits) documented as risk, not yet automated
